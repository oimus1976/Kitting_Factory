# Windows Updateのオフライン適用：設計と検証記録（2026-10-30作成、2026-11-11更新）

## 目的

Stage完了（`WAIT_INET`）後のWindows Updateで、1台ごとのダウンロード待ちと「最新です」と言われて機能更新が出てこない不確実さをなくす。月1回ホストで更新ファイル（`.msu`）を取得してUSBに入れ、各端末では管理者1回の操作で適用する。

## 前提となる事実（2026-10-30確認）

- 24H2・25H2・26H2は同じ保守系列で、毎月の累積更新（LCU）は共通。機能更新は小さな有効化パッケージ（eKB）で切り替わる。
  - 25H2：[KB5054156](https://support.microsoft.com/en-us/topic/kb5054156-feature-update-to-windows-11-version-25h2-by-using-an-enablement-package-4d307e2d-3028-4323-bb46-552cff491643)。前提は24H2で、一定以上のLCU（Q&Aでは26100.5074以降とされる。公式KBで要確認）。
  - **26H2は2026-09-29に一般提供済み**（ビルド26300）。[リリース情報](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information)、[26H2の新機能](https://learn.microsoft.com/en-us/windows/whats-new/whats-new-windows-11-version-26h2)。段階的配信のため、Windows Updateにすぐ出ないことがある。
  - 2026-09のプレビュー更新が「24H2の最終プレビュー」とされている（[KB5124010](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/09/kb5124010-windows-11-24h2-25h2-update)）。24H2のまま配備するのは避ける。
- 24H2系のLCUは「チェックポイント累積更新」方式。カタログの該当KBの`.msu`を**全部同じフォルダー（他のファイルなし）**に置き、DISMで最新のものを指定すると、必要なチェックポイント（KB5043080）から順に自動で適用される（[Microsoft Learn](https://learn.microsoft.com/en-us/windows/deployment/update/catalog-checkpoint-cumulative-updates)、KB5124010の手順）。`.msu`のダブルクリックでは失敗する場合がある（[既知の問題](https://support.microsoft.com/en-au/servicing/os/windows/2024/09/operation-is-not-supported-error-installing-a-post-checkpoint-update-by-double-clicking-the-msu-pack)）。
- 評価VMの現状：24H2、ビルド26100.1742、Enterprise評価版、空き42GB、インターネット到達可。OOBE中に入った更新（KB5124007ほか）が再起動待ちと見られる。

## 決めること

- **決定（2026-10-30）：標準バージョンは26H2。** ベンダー`ClientSoft`・業務システムの26H2での動作確認は別途必要。
- 経緯：配備する標準バージョンは25H2か26H2か。 推奨は26H2（Proのサポートが提供開始から24か月で最も長い）。ただし、ベンダーの`ClientSoft`や業務システムが26H2で動作確認済みかどうかを先に確認する。確認が取れなければ25H2。
- 24H2から26H2へ1つのeKBで直接上がれるか、25H2を経由するかは、カタログで要確認（リリース情報は「24H2と25H2の端末に提供」としている）。

## 26H2決定後の確認結果（2026-10-30）

- 24H2のHome/Proはすでに「更新終了」（[リリース情報](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information)）。26H2のHome/Proのサポートは2028-10-10まで。
- **26H2の有効化パッケージ [KB5121794](https://support.microsoft.com/help/5121794) はMicrosoft Updateカタログでは配布されていない**（Windows UpdateとWSUSのみ。カタログ検索も0件）。24H2・25H2から直接、再起動1回で26H2に上がれる。前提はKB5124010（2026-09-22）以降のLCU。
- 当月のLCUは [KB5134133](https://support.microsoft.com/help/5134133)（2026-10-26、OOB。10月のセキュリティ更新KB5127648を含む累積。24H2/25H2/26H2共通のファイル）。前提のチェックポイントはKB5043080。10/28のKB5127936はプレビュー（非セキュリティ）なので使わない。
- 容量：カタログ表示でKB5134133（x64）5162.1 MB、KB5043080（x64）509.0 MB。媒体（8GB）の空きは7.2GBで収まる。実機用USBは32GB以上を推奨。

### 設計の修正

有効化パッケージをUSBに入れられないため、次の2段構えにする。

1. **重い累積更新（約5GB）はUSBからオフライン適用**（ダウンロード待ちの大部分を解消）。
2. **26H2への切り替えはWindows Update経由**。その前に対象バージョン固定の設定（`ProductVersion=Windows 11`、`TargetReleaseVersion=1`、`TargetReleaseVersionInfo=26H2`）を入れて、「最新です」で止まらずに26H2が提示されるようにする。有効化パッケージは小さいので、ダウンロードは短い見込み（未実測）。

下の「設計」の`EKB\`フォルダーと手順4は、この2段目で置き換える。

## 本庁のインターネット環境での取得手順

スクリプト：[scripts/v06/Get-OfflineUpdates.ps1](../scripts/v06/Get-OfflineUpdates.ps1)（管理者権限不要、Windows PowerShell 5.1）。2026-10-30時点でダウンロードURLの応答（HTTP 200）とサイズを確認済み：KB5043080 509.0MB、KB5134133 4,653.1MB、合計約5.2GB。

1. 持ち運び用USBメモリを用意する。**NTFSかexFAT**で、空き6GB以上（KB5134133は4GBを超えるためFAT32では保存できない）。
2. USBのルートに `Get-OfflineUpdates.ps1` をコピーする。
3. 本庁のインターネットに出られるPCで、USBが `E:` なら次を実行する（ドライブ文字は読み替える）。
   ```
   powershell -NoProfile -ExecutionPolicy Bypass -File E:\Get-OfflineUpdates.ps1 -Destination E:\Updates\LCU
   ```
   - BITSでダウンロードし、ファイル名に含まれるSHA-1で照合し、`E:\Updates\updates-manifest.json`（SHA-256入り）を作る。
   - 途中で切れた場合は、壊れたファイルを削除して同じコマンドを再実行する（照合済みのファイルは再取得しない）。
   - 最後に `PASS:` と出れば完了。
4. **スクリプトを実行できない場合**（組織のポリシーで止められる等）：ブラウザーで [Microsoft Updateカタログ](https://www.catalog.update.microsoft.com/Search.aspx?q=KB5134133) を開き、「2026-10 Cumulative Update for Windows 11, version 24H2 for x64-based Systems (KB5134133)」の「ダウンロード」から表示される2ファイルを `E:\Updates\LCU\` に保存する。照合は持ち帰ってからホストで `-VerifyOnly` を付けて実行する。
5. USBをホストへ持ち帰る。以降（検証用媒体への追加など）は別途承認のうえで行う。

取得結果（2026-11-04にホストで読取照合）：PASS。2ファイルとも長さ・SHA-1・SHA-256が `updates-manifest.json` と一致し、Microsoftのデジタル署名は有効。持ち運び用USBは業務ファイルと同居しているため、VMへ接続せず、検証用媒体へは `Updates\` だけをコピーする。

注意：大容量ダウンロードを庁内ネットワークで行ってよいかは、庁内のルールに従う。`Updates\LCU\` には `.msu` 以外を置かない（DISMが同じフォルダーのチェックポイント更新を自動で探すため）。

## 現場の手順（2026-11-11時点、Pro実機1台で確認した流れ）

1. LANケーブルやWi-Fiにつながずに電源を入れ、OOBEはBYPASSNROでローカル管理者を作る（組織の現行手順）。USBはまだ挿さない。
2. サインイン後、`winver` でバージョンとビルドを控える。
3. **マカフィーをアンインストールする**（プリインストールの場合）。「設定」→「アプリ」→「インストールされているアプリ」から行い、求められたら再起動する。（手順化は利用者の判断。更新やUSBへの影響は未確認）
4. USBを挿し、`Kitting-Start.cmd` を右クリック→「管理者として実行」。`PASS` と `WAIT_INET` を確認する。
5. 外部ネットワークにつなぐ。
6. `Kitting-Update.cmd` を管理者として実行する。`NEXT:` の案内どおり再起動して再実行する。
   - `再起動待ち` と出たら、もう一度再起動する（実機では累積更新の後に2回必要だった）。
7. 設定画面が開いたら「更新プログラムのチェック」→「すべてインストール」を押し、終わったら「今すぐ再起動」で再起動する。電源は切らない（HPのファームウェア更新が含まれることがある）。
8. もう一度 `Kitting-Update.cmd` を実行し、`DONE:` を確認する。
9. USBは「ハードウェアの安全な取り外し」をしてから抜く。

## 設計（当初案）

### USBの構成（追加分）

```
USB\Updates\
  LCU\    当月のLCUの .msu 全部（チェックポイント含む。他のファイルは置かない）
  EKB\    対象バージョンの有効化パッケージ .msu
  updates-manifest.json   ファイル名・SHA-256・KB番号・種類・適用後の期待ビルド・対象バージョン
```

`updates-manifest.json`はホストで月1回、ダウンロード後に作る（小さな準備スクリプト）。

### 端末側の入口

- `Kitting-Update.cmd`（新規）：`Kitting-Start.cmd`と同じ作り（管理者チェック、USBにログ、PASS/STOP表示）。
- `Apply-OfflineUpdates.ps1`（新規）：既存のStage用PS1 4本は変更しない。1回の実行で「次に必要な1段階」だけを行う。
  1. 管理者であること、`state.json`が`WAIT_INET`であること、manifestのハッシュ一致を確認
  2. 再起動待ちがあれば何もせず「再起動してから再実行」と表示（STOPではなく案内）
  3. ビルドが期待値未満なら、LCUをDISMで適用（`/NoRestart`）→「再起動してから再実行」
  4. LCU済みでバージョンが対象未満なら、eKBをDISMで適用 →「再起動してから再実行」
  5. 対象バージョン・期待ビルドに達していれば、対象バージョン固定の設定（`TargetReleaseVersion`等。後の通常更新で意図しないバージョンに上がるのを防ぐ）を入れて `DONE`
- 操作者の手順：`Kitting-Update.cmd`を実行 → 再起動 → もう一度実行、を`DONE`まで繰り返す（通常2〜3回）。自動再起動・自動再実行は、手動で安定してから追加する。
- 残りのドライバーや定義ファイルは、その後の通常のWindows Updateで当てる（量は少ないはず）。
- 状態の`WAIT_INET`→`WAIT_NETWORK`の遷移は、今までどおり既存の`InternetDone`で行う（今回は変えない）。

## 最小検証計画（評価VMで1回）

各手順は実施前に承認を得る。自動再試行はしない。

| 手順 | 内容 | 承認が必要な理由 |
|---|---|---|
| 0 | 標準バージョン（25H2／26H2）を決める | 判断 |
| 1 | Microsoft Updateカタログから当月LCUの`.msu`一式と対象eKBをホストへダウンロード。ファイル名・サイズは取得前に提示する | ダウンロード |
| 2 | 現在のTest-PC（`WAIT_INET`到達済み）でチェックポイントを1つ作る（失敗時にStageをやり直さず戻れるように） | VM操作 |
| 3 | ゲストを1回再起動し、OOBE中の更新の再起動待ちを解消。ビルドを記録 | VM操作 |
| 4 | VMを停止し、媒体へ`Updates\`と新規スクリプト2本を追加（既存ファイル不変を照合。空き容量を事前確認） | 媒体書込 |
| 5 | `Kitting-Update.cmd`を`DONE`まで実行（Codexのコンピュータユース）。各回の開始・終了時刻をUSBログから記録 | ゲスト操作・再起動 |

合格条件：`DONE`表示、対象バージョンと期待ビルドに到達、DISMエラーなし、`state.json`は`WAIT_INET`のまま。各段階の所要時間が分かること（これが初めての実測値になる）。

停止条件：DISMの非0終了（3010＝再起動要求は除く）、ハッシュ不一致、想定外の再起動ループ。ログを取って止める。

検証の限界：評価VMはEnterprise評価版。Proでも同じeKB・LCUの仕組みだが、実機のドライバー更新やベンダー資産との相性は別途確認が必要。

## やらないこと

- Windows Update（オンライン）の挙動の調査やWSUS構築
- 既存のStage用PS1 4本・`Update-Worker.ps1`の変更
- 自動再起動・無人連続実行（手動で安定してから）
